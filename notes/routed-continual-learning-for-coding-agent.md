# Routed Continual Learning：论文核心与 Coding Agent 启示

## 一句话总结

不要让 Coding Agent 无限积累一份全局聊天历史，而要决定：**哪些任务可以共享经验、经验用什么形式保存、什么时候读写，以及什么时候失效。**

## 1. 论文信息与核心观点

- 题名：**Routed Continual Learning**，arXiv:2610.38796v1。
- 作者：Michael Philip、Mahesh Balakrishnan、David Geraghty、David Mao、Vidhya Venkat、Ilya Mironov，均来自 FAIR at Meta。
- 提交日期：2026-10-28。
- 原文：https://arxiv.org/html/2610.38796v1

论文研究的是：Agent 不断执行不同任务时，怎样利用过去的经验，而不是每次从头开始。

它把持续学习拆成两个联合决策：

1. **哪些实例应该共享经验？** 同仓库、同对手，还是整个来源任务流？
2. **经验应该怎样表示？** 保留完整执行历史、提炼策略，还是更新统计模型？

核心不是“让记忆越来越多”，而是**根据任务选择经验的共享范围与学习机制**。这是系统层面的持续学习，不是训练一个新的基础大模型。[§1–3](https://arxiv.org/html/2610.38796v1#S1)

## 2. 为什么不使用一份全局记忆？

假设代码修复、银行客服、销量预测和扑克任务不断交错到来。

- **全部保留为全局历史**：精确细节保留下来了，但每次都读取无关内容，成本高，有限上下文中相关经验还会被挤掉。
- **全部压成一份总结**：读取便宜，但可能丢掉代码路径、工具结果、实体关系或数值证据。
- **每个实例都独立运行**：避免污染，但不能利用以前的探索和教训。

因此作者不寻找一种万能记忆，而是提供多种机制，再用路由决定它们在哪些实例之间共享状态。五种机制是探索阶段选定、确认性实验前冻结的候选库，不是理论上完备的五类记忆。[§4.2](https://arxiv.org/html/2610.38796v1#S4.SS2)

## 3. 系统的四个关键对象

| 对象 | 作用 |
| --- | --- |
| Memory system：记忆机制 | 定义状态的形式，以及读取、更新方法 |
| Cluster：记忆簇 | 某种机制的独立实例，拥有自己的状态、配置和适用范围 |
| Router：路由器 | 每个实例开始前，选择复用旧簇或创建新簇 |
| Context Memory Adapter | 将任务字段绑定到通用记忆接口，验证证据并把记忆加入 Agent 上下文 |

例如，仓库 A 和仓库 B 可以都用 ICL 机制，但分别拥有独立的簇。**机制决定怎么记，簇决定谁共享。**

Adapter 不是 LoRA，也不修改基础 LLM 权重。它不替 Agent 操作环境或提交答案，只提供上下文建议与记忆读写接口。[§3–4](https://arxiv.org/html/2610.38796v1#S3)

## 4. 五种固定记忆机制：为什么设计、什么时候用

### 4.1 ICL：保留精确历史

**要解决的问题**：有些经验需要精确细节，过早总结可能丢掉未来需要的信息。

- 保存有序的可见任务、Agent 回复与动作、工具结果和反馈。
- 新轨迹追加到历史，读取时将保留历史放入上下文。
- 实验每个 ICL 簇有 100K-token 预算，超预算优先移除最旧消息。
- 适合同环境的连续任务：代码仓库、数据库探索、同一个扑克对手。
- 不适合只需要几条通用策略、却不得不反复读取大量原始记录的情况。

**判断问题：下一次是否可能需要过去发生的精确细节？**

### 4.2 ReasoningBank：提炼可迁移的方法

**要解决的问题**：不同案例不共享具体事实，却可能共享解决步骤与失败教训。

- 完成轨迹后，由同一 backbone LLM 根据可见内容自判成功或失败。
- 提取最多三条记忆，包含 title、description、content。
- 用冻结的本地 embeddings 找一个最相似的历史 request，读取那次经验提炼出的全部条目。
- 适合相对独立但方法相似的任务，例如客服流程、工具使用与避错策略。
- 不适合替代精确仓库事实；自判与抽象也可能错误。

**判断问题：新任务需要的是过去那个案例，还是案例教会的方法？**

### 4.3 Hierarchical Regression：学习重复数值规律

**要解决的问题**：保留旧数字不等于从数字中学习，数值预测需要把多次真实观测结合起来。

- 输入是稳定 key 下的标量结果、分类因素和可选时间，例如商品、地区、年份、实际销量。
- 提取器生成 typed records，固定 PyMC 运行时做分层回归并随新结果重新拟合。
- 同时池化全局、实体、因素和时间效应，将预测、噪声估计与近期观测作为建议提供给 Agent。
- 适合需求、销量等重复数值预测；论文用于 Sales Prediction。
- 不能把 Agent 以前的预测当成真实结果继续学习。

**判断问题：实体身份已知，是否需要从重复的真实数值中估计规律？**

### 4.4 Hierarchical Discrete-Event State：学习无事件概率曲线

**要解决的问题**：不同时间区间的无事件概率有关联和单调约束，不能当成彼此独立的数字。

- 保存群体、特征、context、支持权重以及有序区间的可见无事件概率测量。
- 用 PyMC 分层离散 hazard 模型，结合不同群体和来源的证据。
- 读取时提供请求目标的有效单调概率曲线。
- 适合“截至某个时间仍未发生事件”的估计，论文用于 Cohort Studies。

教学直觉：如果 h_j 是第 j 个区间的条件事件概率，则 S_k=∏(1−h_j)，乘积取 j≤k，表示截至第 k 段仍无事件的概率。这个标准关系解释单调性，不是论文完整模型公式。

**判断问题：目标是不是具有时间顺序约束的无事件概率，而不是普通标量？**

### 4.5 Persistent-Entity State：追踪噪声背后的持久实体

**要解决的问题**：每轮观测数量、顺序不同且有噪声，没有可靠 ID；必须先判断哪些观测属于同一个实体。

- LLM 提取器只复制可见测量，不负责跨轮关联。
- 固定运行时做不确定度感知匹配，维护实体身份估计与 River Bayesian linear regression。
- 读取时提供相关实体候选、支持数量、出现范围和预测值，并标明不确定性。
- 适合间歇观测的发射源等，论文用于 Blind Spectrum Monitoring。
- 与普通回归的区别：不是直接学习已知实体，而是先处理实体对应关系。

**判断问题：是不是连“这次观测与上次是不是同一个实体”都不确定？**

五种机制的详细依据：[§4.2](https://arxiv.org/html/2610.38796v1#S4.SS2)、[附录 B.2](https://arxiv.org/html/2610.38796v1#A2.SS2)、[附录 D](https://arxiv.org/html/2610.38796v1#A4)。

## 5. 新记忆簇如何创建？

不是先收集全部历史再跑 k-means，而是每个实例到来时在线决策。

### 路由输入

Router 看见当前 prompt、response schema、固定机制描述，以及每个已有簇的：

```text
ID、机制类型、不可变的 scope 描述、已完成轨迹计数
```

它看不到簇内部的完整历史或统计状态。这里的 summary 更像档案标签，不是不断重写的经验摘要。

固定提示要求：只有旧簇范围适用、且经验可能无冲突地帮助当前实例时才复用；否则创建新簇，并选择合适机制、描述未来适用范围。Router 是 prompted, not trained，没有显式最优聚类规则或奖励驱动训练。

### 创建与初始化

创建响应示意：

```json
{
  "kind": "new",
  "cluster_id": null,
  "system_id": "icl",
  "description": "仓库 A 的代码结构、测试流程与修复经验"
}
```

其中 description 是自行构造的例子。运行时创建新 ID、独立初始状态与固定机制；不会默认复制其他簇经验。复用旧簇时则指定已有 cluster_id。

- **ICL**：无需配置，第一实例完成后即可把轨迹存入历史。
- **RB 和数值机制**：第一实例按原 prompt 执行，轨迹作为 warm-up；只有首次复用才配置 adapter，若从未复用就不配置。
- 数值 adapter 根据 warm-up 和当前任务结构绑定字段，回放、验证；配置失败最多允许一次修复，成功后配置在簇生命周期内冻结。

完整流程：

```text
新实例 → 一次路由 → 创建/复用簇 → 必要时首次配置
       → 读取记忆并加入上下文 → Agent 正常执行
       → 从可见证据更新所选簇
```

整个实例的簇分配不变，目前只读写一个簇和一种机制。高层统一接口为：

```text
z_t       = read_m(S_(c,t), x_t; θ_c)
S_(c,t+1) = update_m(S_(c,t), τ_t; θ_c)
```

z_t 是加入上下文的文本，S 是簇状态，θ 是固定后不变的语义配置。具体证据 ingestion 时机会因机制不同而变化，例如 PES 会处理 query-start 的当前测量，不能理解为所有机制都只在任务结束时写一次。

基础 LLM 权重不更新，但外部统计模型确实会拟合或在线更新。隐藏评估奖励不提供给学习系统，正常交互公开的反馈仍可使用。[§3–4](https://arxiv.org/html/2610.38796v1#S3)、[附录 B.1](https://arxiv.org/html/2610.38796v1#A2.SS1)、[D.1](https://arxiv.org/html/2610.38796v1#A4.SS1)

## 6. 实验证明了什么？

### 数据与对照

398 是**实例数量，不是 398 类任务**：

| 来源 | 实例数 |
| --- | ---: |
| Codebase Adaptation | 19 |
| Cohort Studies | 20 |
| Database Exploration | 40 |
| Exploitable Poker | 120 |
| Sales Prediction | 12 |
| Blind Spectrum Monitoring | 90 |
| Banking | 97 |

七个来源随机交错，但保持每个来源内部的顺序。四模型分别完成五次匹配 rollout；主要对照为：

1. Stateless ICL：每次重置。
2. Global ICL：整个混合流共用历史。
3. Routed ICL：分簇，但只能用 ICL。
4. Routed CL：分簇并可选五种机制。

### 主结果

| 模型 | Global ICL 奖励 | Routed ICL | Routed CL | Global ICL 成本 | Routed CL 成本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Gemini 3.7 Flash | −0.030 | 0.211 | 0.213 | $200.14 | $61.08 |
| GPT-5.6 Sol | 0.168 | 0.387 | 0.464 | $456.22 | $125.99 |
| Opus 4.7 | 0.092 | 0.209 | 0.243 | $708.78 | $222.72 |
| Opus 5 | 0.169 | 0.340 | 0.401 | $914.36 | $316.61 |

以上为五次均值，成本是每个 398-instance rollout 的估算 API 美元成本。[表 1](https://arxiv.org/html/2610.38796v1#S1.T1)、[表 6](https://arxiv.org/html/2610.38796v1#A3.T6)

- CL 相对 Global ICL 增加 **0.151–0.296 个归一化奖励点**，即满分 1 的约 15–30%；不是原奖励相对增长 15–30%。
- API 成本降低约 **65–72%**，包括路由、配置、抽取和记忆生成调用，以及缓存定价；不是总系统成本或延迟降低。
- 奖励对六种 CL-Bench 使用外部 stateless GPT-5.4 参考归一化，银行使用 native reward；七来源等权，不按实例数加权。
- 另一个 stateless-reference gain 指标使用本文相同模型、相同种子的 Stateless ICL 为参考，不能与主指标混用。[A.6](https://arxiv.org/html/2610.38796v1#A1.SS6)

**关键解释：很大一部分收益来自分簇，而不是全部来自五机制选择。** CL 相对 Routed ICL 的配对奖励增益分别是 0.002、0.076、0.034、0.061。Gemini 增益很小且有一次退化；Opus 4.7 的 CL 比 Routed ICL 贵约 5%。因此“完整机制库始终大幅胜过简单方案”不成立。[表 5](https://arxiv.org/html/2610.38796v1#A3.T5)

## 7. 失败、局限与不能过度解读的地方

- **合并过度**：Gemini 曾把不同代码仓或扑克对手合并，导致混杂与更长历史。
- **碎片化**：GPT 在四次银行流里创建 23–27 个簇，Opus 4.7 两次创建 23 和 86 个簇；创建更多不代表学得更好。
- **机制选择会错**：部分模型在 Code 上选择 RB，表现落后于 Routed ICL；精确代码经验有时比抽象策略更重要。
- **分簇不总帮助检索型记忆**：Routed RB 相对 Global RB 没有一致奖励收益，却增加 8–29% 成本；这项比较只有三次匹配 rollout。
- **并发尚未验证**：实验顺序运行，每次 rollout 各模型角色用一个 backbone；没有验证同时更新、stale reads 或跨模型共享。
- **基准协议有修改**：Sales 重置可写环境，Code 隔离历史 Git 数据与隐藏测试，所以不能与历史 CL-Bench 严格协议等价。
- **不能直接推广生产收益**：结果来自有限混合 benchmark，五次 min/max 也不是置信区间。长期漂移、失效策略与完整基础设施成本未充分验证。

来源：[§6–7](https://arxiv.org/html/2610.38796v1#S6)、[附录 A.4](https://arxiv.org/html/2610.38796v1#A1.SS4)、[表 8](https://arxiv.org/html/2610.38796v1#A3.T8)。

## 8. 与 RAG 的区别

典型文档 RAG 主要决定“当前问题检索哪些文档”；Routed CL 先决定“与哪群经验共享哪种状态”，再由具体机制读取和更新。

两者不互斥：ReasoningBank 本身做相似度检索，RAG 也可以作为一种记忆机制。数值机制的特点则是拟合累积证据，而不是只拿回相似文本。论文没有证明它胜过所有 RAG 系统。

## 9. 对 Coding Agent 最值得借鉴的四点

以下为工程建议，不是论文原样实现。对于普通 Coding Agent，优先借鉴 ICL 的精确证据与 ReasoningBank 的策略记忆，不必强行加入三个数值机制。

1. **先隔离，再共享。** 同仓库的结构、测试命令和执行经验可以共享；不同仓库不能因为技术栈相似就混用。权限边界应由硬规则决定，而不是交给 LLM。
2. **事实与策略分开。** 仓库事实保存精确路径、命令、结果、来源与版本；策略保存可迁移的排查步骤和失败教训。避免把一次案例中的细节当成通用规则。
3. **任务前读取，任务后提炼。** 开始时只注入有限、相关、有来源的记忆；结束时从实际轨迹中提取值得保留的内容，并结合测试、typecheck、命令输出或人工反馈验证，不能只靠 LLM 自判成功。
4. **允许记忆过期。** 代码会变化，历史事实必须带作用域、版本、验证状态和失效条件。旧记忆应作为待核对的线索，不能覆盖当前代码或用户指令。

## 10. 一个面向 Coding Agent 的最小实现

```text
当前任务工作记忆：保存本次探索过程
仓库级事实与证据：保存路径、命令、约束、来源、版本
策略库：保存可复用方法、适用条件、失败教训
```

任务开始：确定仓库与权限 → 检索相关证据和少量策略 → 检查过期风险 → 按上下文预算注入。

任务结束：提取候选记忆 → 区分事实、假设和策略 → 验证并记录来源 → 去重或处理冲突。

## 11. 工程建议的边界

- 上述三层存储、版本失效及同时读取事实与策略，是面向 Coding Agent 的工程建议，不是论文已经验证的完整实现；论文当前每次实例只读写一个簇和一种机制。
- 论文中的 Coding 结果提醒：精确历史有时比抽象策略更有用，不能默认压缩记忆一定更好。
- 论文在 398 个混合任务实例、四模型、五次匹配运行中，相对 Global ICL 增加约 0.151–0.296 个归一化奖励点，估算 API 成本降低约 65–72%。这些是整个混合任务流的结果，不是 Coding Agent 专项收益保证。
- 分布式并发、跨模型共享与长期代码漂移没有得到充分实验验证。
